# Bancwr Threat Model

Status: current

Baseline: `diogel-io/bancwr` `master` at `b44bcaf`

This document covers what Bancwr protects, where its trust boundaries are, what an attacker at
each boundary can do, what stops them, and what does not yet. To report a vulnerability, see
[`SECURITY.md`](../SECURITY.md).

## How to read and maintain this document

- Assets are `A`, boundaries `B`, adversaries `X`, and threats `T`. The IDs are stable: a row that
  no longer applies is marked as such, never renumbered.
- Each control names the code that enforces it and, where one exists, the test that holds it
  (section 7). A control with no test says so.
- **Any change that adds or changes an asset, a trust boundary, or a control updates this file in
  the same pull request**, and moves the baseline above if it re-checks the whole document.
- Only limits that are already public, in the READMEs or open issues, are written here. A newly
  found weakness is reported privately under [`SECURITY.md`](../SECURITY.md) and fixed first, and
  added here afterwards.

The design behind sign-in and the proxy is the sign-in decision record,
`diogel-io/workspace` `10-products/bancwr/architecture/nostr-session-auth-adr.md` (#23). Where it
and this document differ about current behaviour, this document and the code win.

## Scope and method

In scope: Bancwr as `compose.yaml` ships it. One bunker container (Rust, `backend/`) and one
frontend container (Nuxt and Nitro, `frontend/`) on one host, joined by the compose network. A
TLS reverse proxy run by the operator sits in front of the frontend. The bunker holds one signing
key, signs NIP-46 requests that arrive over Nostr relays, and serves an administration API that
only the frontend calls.

Out of scope: running several frontend instances, hosted Bancwr, and the operator's reverse proxy
and host hardening beyond what Bancwr requires of them. An independent review is a separate task
(diogel-io/workspace#175).

Method: every row was written by reading the code named on `master` at the baseline commit, and
the READMEs. Nothing here was penetration-tested.

## 1. Assets

| ID | Asset | Where it lives | Why it matters |
|----|-------|----------------|----------------|
| A1 | The bunker's private keys | The primary identity's key at rest, only as XChaCha20-Poly1305 ciphertext under A10 in `bunker-key.enc` beside the database (`./data` under compose), written once by `bunker import-key` from `BUNKER_NSEC_FILE` or `BUNKER_NSEC`, which the operator then removes (`backend/src/key_store.rs`, `docs/operating.md`; #94). Decrypted at start into bunker memory (`backend/src/signer.rs`). Copied, still as that ciphertext, into every backup archive (#95). Each further identity (#103) is added with `bunker import-key --add`, encrypted the same way under the same A10, and stored in the database (`identities`, `key_file`), so A8's archives carry it; at start it must decrypt to the public key its row records, or the bunker stays locked (`backend/src/main.rs`, `backend/src/keyring.rs`) | Whoever has one is that Nostr identity, permanently: Nostr has no key rotation or revocation |
| A2 | The ability to make the bunker sign, encrypt or decrypt | The NIP-46 handler (`backend/src/nip46.rs`): `sign_event`, and the NIP-44 and NIP-04 encryption methods (#97). For a kind that needs approval, `sign_event` signs only when an administrator approves it (`POST /api/bunker/approvals/:id/approve`; #102) | An attacker does not need A1 if they can get events signed with it, or messages sent to it decrypted |
| A3 | The proxy secret | `BANCWR_PROXY_SECRET` on the bunker, `NUXT_PROXY_SECRET` on the frontend, the same value | With it, anyone who reaches the bunker can call its API as any identity |
| A4 | The session-sealing password | `NUXT_SESSION_PASSWORD` on the frontend | Seals the session cookie |
| A5 | Live sessions and login challenges | Sessions: files in `./sessions` on the host, each under the SHA-256 of its id, with the pubkey and expiry (`frontend/server/utils/auth/sessions.ts`, `session-store.ts`; #100). Challenges: frontend process memory (`challenges.ts`) | A live session id is a signed-in user |
| A6 | The member registry and roles | SQLite at `DATABASE_PATH` (`backend/src/registry.rs`, `backend/src/db.rs`), and a snapshot of it in every backup archive (`backend/src/backup.rs`; #95) | Decides who may do what |
| A7 | Connection tokens and connections | SQLite, and backup archives. Tokens are stored as a SHA-256 hash only (`nip46.rs`, `hash_secret`). A restore revokes every connection and unused token (#95). Each is for one identity (#103), and members' grants of identities (`identity_access`) sit beside them | A connection may sign the kinds it was granted, as its identity |
| A8 | The signing log, audit events and configuration | SQLite and backup archives: the log of signatures; audit events for every token, connection, team, relay and retention change, each written in the transaction that made the change (`backend/src/audit.rs`, `backend/src/db.rs`; #96); the bunker relays; the log retention policy. Copies leave the bunker only as administrators' exports (`backend/src/logs_api.rs`) | Accountability, and where NIP-46 traffic goes |
| A9 | The first-administrator setting | `BANCWR_ADMIN_PUBKEY` | Seeds the first administrator when there is none |
| A10 | The root credential | 32 random bytes as hex, in the file `BANCWR_ROOT_KEY_FILE` names: under compose the `bancwr_root_key` secret from `./secrets`, read-only, owned by UID 65532 with mode `0400`. Read from a file only, never the environment. Zeroed in memory when dropped (`backend/src/key_store.rs`; #94) | With A1's ciphertext it is A1. Without it, a copy of `./data` or a backup holds no usable key |
| A11 | The backup passphrase | At least 16 characters in the file `BANCWR_BACKUP_KEY_FILE` names: under compose the `bancwr_backup_key` secret from `./secrets`. Read from a file only, refused when it equals A10, zeroed in memory when dropped. scrypt of it, with a per-archive salt, is the XChaCha20-Poly1305 key of each archive (`backend/src/backup.rs`; #95) | With an archive it is A6, A7 and A8 as at the backup, and A1's ciphertext. Without A10 too, still no usable key |
| A12 | Requests waiting for approval | In bunker memory only (`backend/src/approvals.rs`; #102): each `sign_event` held, with its event content, connection, app key and request id, at most 20 per connection and 200 in all, until decided, timed out or cancelled. Never written to disk or a backup; a restart drops them | Their content is what an app means to publish. Approving one makes the bunker sign it (A2) |

## 2. Trust boundaries

| ID | Boundary | Crossed by | Enforced in |
|----|----------|------------|-------------|
| B1 | Browser ↔ operator's TLS reverse proxy | Every request to the console | The operator's proxy. The frontend refuses to start without an `https://` `NUXT_SITE_ORIGIN`, except on localhost (`frontend/server/utils/auth/config.ts`) |
| B2 | Browser ↔ Nitro frontend | Sign-in, the session cookie, every console call | `frontend/server/api/auth/*`, `frontend/server/utils/auth/*` |
| B3 | Nitro proxy ↔ bunker API | Every `/api/bunker/*` call, signed with A3 | `frontend/server/api/bunker/[...].ts`, `frontend/server/utils/auth/proxy-signature.ts`, `backend/src/proxy_auth.rs` |
| B4 | Bunker ↔ relays ↔ NIP-46 apps | NIP-46 requests and responses, kind 24133 | `backend/src/relay.rs`, `backend/src/nip46.rs`, `backend/src/bunker_relays.rs` |
| B5 | A member's own signer ↔ the browser | The sign-in event only (NIP-07 extension or NIP-46 remote signer) | The member's signer; Bancwr never sees the member's key |
| B6 | Containers ↔ host and operator | Environment, files, `./data` (with A1's ciphertext), `./secrets` (A10, A11), `./sessions` (A5), backup archives written to and restored from standard input and output, images pulled from GHCR | The host; non-root distroless images (#16) |

The bunker's port is not published by `compose.yaml`: only the frontend container reaches it, over
the compose network. The frontend is published on `127.0.0.1:3001` only, for the reverse proxy.

## 3. Adversaries

| ID | Adversary | Starts with |
|----|-----------|-------------|
| X1 | Network attacker | Can watch or alter traffic between the browser and the host |
| X2 | Unauthenticated web visitor | Can reach the console's sign-in page; may run a malicious site the member visits |
| X3 | Registered member beyond their role | A real session as a viewer or signer |
| X4 | NIP-46 app | A connection token, or a live connection, for some kinds |
| X5 | Malicious or compromised relay | Sees and can drop, delay or replay NIP-46 traffic through it |
| X6 | Direct caller to the bunker | Can reach the bunker's port, without A3 |
| X7 | Holder of a copied session cookie | The cookie, without the browser it came from |
| X8 | Host or operator access | The environment, files and containers |
| X9 | Supply-chain attacker | A dependency, base image or published image |

## 4. Threats and controls

| ID | Threat | Boundary | Adversary | Controls |
|----|--------|----------|-----------|----------|
| T1 | Sign in as someone else by forging or replaying a sign-in event | B2 | X1, X2 | Sign-in is a NIP-98 event (kind 27235) bound to the login URL taken from `NUXT_SITE_ORIGIN`, never from `Host`; to `POST`; and through the `payload` tag to a body carrying a server challenge. The challenge is single-use and lives 300 s: once the body parses and names a string challenge, it is consumed before the event is checked, whether or not the rest passes. A body that does not parse, or names no string challenge, is refused without consuming anything. `created_at` must be within 120 s past and 30 s future. The signature is verified on a freshly parsed object (`frontend/server/utils/auth/login-event.ts`, `challenges.ts`, `constants.ts`) |
| T2 | Sign in with the bunker's own key, so that a NIP-46 app able to sign a login event becomes an administrator | B2, B4 | X4 | The bunker's key is refused at sign-in (403 `bunker_key`), can never be registered, and is refused as `BANCWR_ADMIN_PUBKEY` at start (`login-event.ts`, `backend/src/server.rs`, `backend/src/config.rs`). See "Why not the bunker's key?" in the README. So is every identity's key (#103): the status lists them all for sign-in, a member's key cannot be added as an identity, and an identity's key cannot be added as a member or be `BANCWR_ADMIN_PUBKEY` (`frontend/server/utils/auth/members.ts`, `backend/src/db.rs`, `backend/src/main.rs`) |
| T3 | Steal or reuse a session | B1, B2 | X1, X2, X7 | The cookie is `HttpOnly; Secure; SameSite=Strict; Path=/`, 12 h, sealed with A4, and holds only a random 32-byte session id (`frontend/server/utils/auth/session.ts`). Signing out or signing in again revokes the id server-side: its entry is deleted before the response, so a copied cookie stops working, across a frontend restart too (`sessions.ts`; #100). The store holds only a SHA-256 of each id, so a copy of `./sessions` yields no id to put in a cookie, and a cookie still needs A4. HTTPS is required (B1), except plain HTTP to `localhost`, `127.0.0.1` or `[::1]` |
| T4 | Keep access after removal or demotion | B2, B3 | X3 | The role is read from the registry on every request, never stored in the session (`frontend/server/api/auth/session.get.ts`, `backend/src/proxy_auth.rs`). Removing a member, or making them a viewer, revokes their NIP-46 connections and tokens (`member_removed`, `role_changed`), in the transaction that changes them (`backend/src/db.rs`). An administrator changes a role in place with `PATCH /api/bunker/team/:id` (`backend/src/server.rs`; #99), and the new role applies from the member's next request |
| T5 | Do more than the role allows | B3 | X3 | The bunker applies one route-by-role matrix to the verified identity (`proxy_auth.rs`, `Access`; table in `backend/README.md`). The console's page gating is cosmetic; the bunker enforces. The last administrator cannot be removed or demoted, checked in the statement that would change them so it cannot race (`backend/src/server.rs`, `backend/src/db.rs`; #99). Reading, exporting and pruning the log are the administrator's only (#96). Approving or rejecting a request held for approval is the administrator's only; a signer lists only their own requests waiting (`backend/src/approvals_api.rs`; #102). Renaming identities and granting or removing a member's grant are the administrator's only (`backend/src/identities_api.rs`; #103) |
| T6 | Call the bunker's API directly, or claim an identity to it | B3 | X6 | Every `/api/bunker/*` route needs `x-bancwr-identity`, `x-bancwr-timestamp`, `x-bancwr-nonce` and `x-bancwr-signature`: HMAC-SHA256 under A3 of `v2`, the timestamp, the nonce, the method, the path with query, the identity, and the SHA-256 of the body exactly as sent. The frontend signs the raw body it forwards, never a re-serialised one, with a fresh 128-bit nonce per request. The bunker reads at most 2 MiB of body to check it (413 `payload_too_large` above that), compares the signature in constant time with a 30 s window, and accepts each nonce once across every guarded route of the process (401 `replayed` after that). A timestamp from before the bunker process started is refused (401 `stale`), so a restart, which empties the in-memory nonce set, does not accept a request signed before it. Any other failed check is 401 `not_authenticated` with the reason (`missing`, `malformed`, `stale`, `bad_signature`). A pubkey that is not registered, or whose role the route does not allow, is 403, as is the frontend's own `service` identity on any route but the bunker's status and the member-key lookup that sign-in needs. A failed registry lookup is 500. The bunker does not start without A3, and the frontend refuses a secret under 32 characters (`proxy_auth.rs`, `config.rs`, `proxy-signature.ts`). The proxy builds these headers from the session, never from the browser (`[...].ts`). The bunker port is not published (B3). Only `/health` is open |
| T7 | Use the console from another site | B2 | X2 | `SameSite=Strict` on the session cookie, and no CORS layer on the bunker (`server.rs`), so a browser on another origin cannot call it |
| T8 | Have the bunker sign anything for anyone | B3, B4 | X4, X6 | There is no `POST /sign` route. NIP-46 needs a connection token an administrator issued: single-use, 1 hour to 7 days, for a member who can sign, and limited to the kinds it names. There is no "everything" grant. The token secret is shown once and stored as a hash. A connection may sign only the kinds granted, and only while its member may sign (`nip46.rs`, `backend/src/connections_api.rs`; #53) The NIP-44 and NIP-04 encryption methods are permissions of their own, named on the token as NIP-46 names them, and nothing is encrypted or decrypted without the method's permission. They refuse as the other party the key of any NIP-46 app that has connected, active or not, so an app cannot decrypt or build the traffic between other apps and the bunker (T9). Viewers hold no tokens or connections, so never these permissions (`nip46.rs`, `connections_api.rs`, `backend/src/db.rs`; #97) A token may give its connection a lifetime of 1 hour to 365 days, counted from when the app connects. Once it passes, every request is refused, before and after the connection is marked revoked as `expired` (`active_nip46_connection` excludes it), and it is marked at the first refused request, at start, hourly, before listing and before a reconnect (`db.rs`, `nip46.rs`, `backend/src/main.rs`; #98) Each connection is rate limited: a token bucket of 60 requests a minute with a burst of 20 by default, or what the token set (1 to 600 a minute, burst 1 to 100, no unlimited setting). `sign_event` and the four encryption methods count, checked once the connection is found and before its permissions or any work, so a refused request signs, decrypts and records nothing. Connections from before the upgrade get the default. Refusals are counted in `/api/bunker/metrics` (`backend/src/rate_limit.rs`, `nip46.rs`, `connections_api.rs`; #101) A token may mark some of its kinds as needing approval, copied to the connection. A `sign_event` for one, past the rate limit and the permission check, is held (A12) and answered with a NIP-46 auth challenge; it is signed only when an administrator approves it. Approval names the event id the administrator was shown, so a different event cannot be approved, and the connection is checked again at that moment, so an ended or narrowed connection's request is cancelled rather than signed. A request nobody decides times out and signs nothing (`backend/src/approvals.rs`, `approvals_api.rs`, `nip46.rs`, `relay.rs`; #102) A token is issued for one identity, only for a member who may use it; the connection signs, encrypts and decrypts only as that identity, answers only requests addressed to it, and stops working when its member's grant is removed, which also revokes it. Once a bunker holds several identities a signer needs a grant for each; administrators may use all (`backend/src/db.rs` `IDENTITY_ALLOWED`, `nip46.rs`, `relay.rs`, `connections_api.rs`; #103) |
| T9 | Read or tamper with NIP-46 traffic | B4 | X5 | Requests and responses are encrypted end to end between app and bunker (NIP-44, or NIP-04 for older clients) and signed (`relay.rs`). Relays saved in the console must be `wss://` except on this machine (`bunker_relays.rs`, `validate`); `NIP46_RELAYS` is used as given, without that check (section 5). The client answers relay NIP-42 AUTH challenges (`relay.rs`). A connected app holding the encryption methods still cannot read or write this traffic: those methods refuse a NIP-46 app's key as the other party (T8; #97). A relay can still drop or delay traffic |
| T10 | Pass an app off as something it is not | B4 | X4 | An app's name, URL and image are marked unverified (`metadata_verified: false`) and never used to decide anything (`nip46.rs`) |
| T11 | Read or change the key, secrets or database on the host | B6 | X8 | Not prevented for whoever controls the host: see section 5. A1 is on disk only as ciphertext under A10, so a copy of `./data`, a database backup or `.env` alone does not yield it; A10 is a separate secret file, kept out of those backups (`backend/src/key_store.rs`, `docs/operating.md`; #94). The key file is written `0600`, never replaced by an import, and authenticated with its public key as associated data, so an altered file fails to decrypt (T14). The bunker never runs from a plain key: while `BUNKER_NSEC` or `BUNKER_NSEC_FILE` is set it stays locked, so the operator must remove the plain copy (`backend/src/main.rs`). A backup archive is encrypted under A11, never holds A10, and holds A1 only as that ciphertext, so an archive and A11 together still do not yield A1 (`backend/src/backup.rs`; #95). A copy of `./sessions` alone yields no session: it holds hashes of the ids, not the ids (#100). Containers run as UID 65532 on distroless images with no shell (#16) |
| T14 | Make the bunker sign with a key it should not have, or keep signing after its key storage is broken or altered | B6 | X8 | Fails closed. With A10 missing, unreadable or malformed, the key file missing, unreadable, malformed or altered, the wrong A10, a decrypted key that does not derive the recorded public key, or a plain key still configured, the bunker starts locked: it holds no key, NIP-46 does not start, and every route but `/health`, the status and the sign-in member lookup answers 503. `/health` answers 503 with fixed wording that names no path and no key material, which `bunker healthcheck` prints, and the status's `signer` check fails with it (`backend/src/key_store.rs`, `backend/src/main.rs`, `backend/src/server.rs`, `backend/src/health.rs`, `backend/src/healthcheck.rs`; #94) |
| T15 | Restore an old or altered archive to get access back that was removed, or to plant a database or key | B6 | X3, X8 | `bunker restore` checks everything before writing: the archive's header (format, version, scrypt cost under a ceiling of 1 GiB, salt, public key, schema version, time) is the AEAD's associated data, so any change, the wrong A11 or truncation is refused; the database must pass `PRAGMA integrity_check` and be no newer than the binary; the key file must record the header's public key; and A10 must decrypt it. It writes only into a data directory with no database, journal or key file, never replacing one. It then revokes every NIP-46 connection (`restored`) and every unused token, so no app or token shut out since the backup comes back. Members removed and roles lowered since the backup do come back (section 5) (`backend/src/backup.rs`, `backend/src/db.rs`, `backend/src/main.rs`; #95) |
| T16 | Erase or hide what was done, or use the log against the people in it | B2, B3, B6 | X3, X8 | Every change to who may sign is recorded as an audit event in the same transaction as the change, so a change cannot happen unrecorded (`backend/src/db.rs`, `backend/src/audit.rs`). Only administrators page, export or set retention (T5). A retention policy cannot go under 30 days or 10,000 rows, and every change of policy, every prune that deletes rows and every export is recorded with who and what. In CSV exports a value a spreadsheet would read as a formula is prefixed with `'`, so a member's or app's name cannot run code when an export is opened. A connection that reaches its lifetime is recorded as revoked with the reason `expired` and no actor, at the time it expired (#98). Every decrypt a NIP-46 app asks for is recorded, with the member, connection, app and the other party's key, before the bunker decrypts, and nothing is decrypted if the record cannot be written (#97). An app refused for its rate limit is logged and recorded as `connection_rate_limited`, with no actor, at most once a minute per connection, so a flood cannot flood the log (#101). Every request held for approval is recorded as `approval_requested` before it waits, and refused if that cannot be written; its end is recorded as `approval_approved` or `approval_rejected` with the administrator and their note, `approval_expired`, or `approval_cancelled`, with the request, kind and event id and never the content (#102). Event content is never recorded, nor a decrypt's plaintext or ciphertext. The proxy streams an export with only its content type and file name, and `no-store` (`frontend/server/api/bunker/[...].ts`, `frontend/server/utils/download.ts`). Not prevented: an administrator shortening retention to the floor, or anyone with the host editing the database (section 5) (`backend/src/logs_api.rs`; #96). Identities added, renamed, granted and their grants removed are recorded, and every signature names the identity that made it, in the log and the export (#103) |
| T12 | Ship a vulnerable or tampered image | B6 | X9 | Release images are built from a tag, pass the test suite, and are gated on fixable critical and high Trivy findings before anything is published. Published images are scanned weekly (`docs/releasing.md`, `.github/workflows/release-image.yml`, `trivy-security.yml`). Images are not yet signed (section 5) |
| T13 | Lock everyone out | B2, B3 | X3 | The last administrator cannot be removed or demoted (#99). `BANCWR_ADMIN_PUBKEY` seeds an administrator when none exists, and never re-adds or demotes anyone afterwards (`backend/src/main.rs`, `backend/src/db.rs`) |

## 5. Known limits and accepted risks

These are true of Bancwr today. Each names what would change it.

| Limit | Consequence | Changes with |
|-------|-------------|--------------|
| The bunker key (A1) and the root credential (A10) are both on the host | Anyone who controls the host (X8) can read both files, and so the key. Encryption at rest (#94) protects copies of `./data` and its backups, not a compromised host | Not planned in 0.2.0: KMS or HSM support would change it |
| A1 stays in bunker memory without being fully erased | `nostr` 0.39 `Keys` caches a `secp256k1` keypair that is not erased on drop. The decrypted bytes, A10 and each `SecretKey` are erased (`backend/src/signer.rs`) | Not planned |
| A key that was plain text before 0.2.0 may have been copied | Importing it does not undo a copy already in a backup of `.env` or of the host, and Nostr cannot rotate a key | Not planned: `docs/operating.md` says so in the migration |
| Every app of an identity signs as that identity | "For a member" is attribution in the signing log, not a separate identity. A bunker may hold several identities (#103), each shared by every connection issued for it | Not planned |
| One root credential and one process hold every identity | Whoever controls the host (X8), or reads the bunker's memory, has every identity it holds, not one. Separate bunkers remain the answer when that is not acceptable | Not planned in 0.3.0 |
| An identity cannot be removed | Once added, an identity stays in the database and in backups; it can be renamed and its connections revoked | Not planned in 0.3.0 |
| One frontend instance only | Live sessions are files in that instance's `./sessions`, which two instances cannot share. A restart keeps them; login challenges are in memory, so a sign-in under way when the frontend restarts must start again | Not planned: several instances, or a shared store, were left out of #100 |
| A refused request still costs the bunker work | Past its rate limit (T8), an app's request is still decrypted, its refusal encrypted and published to the relay: the limit bounds signing and decrypting for the app, not relay traffic | Not planned in 0.2.0 |
| Keys with no connection are not rate limited | A request from a key with no active connection is refused (`Not connected`) after one indexed lookup, however often it comes | Not planned in 0.2.0 |
| Rate limits are per connection, in memory | A restart refills every bucket, and a member with several connections has a limit for each | Not planned in 0.2.0 |
| Approval is lost on restart | Requests waiting for approval (A12) are in memory only, so a restart drops them: the app gets no answer, and the audit log keeps an `approval_requested` with no outcome. Accepted so event content is never stored | Not planned in 0.3.0 |
| An app may give up before approval | nostr-connect waits only as long as the app's own timeout. If it gives up, a later approval still signs and sends the event, but nobody receives it; the signature is in the log | Not planned: the console shows how long each request has waited |
| Administrators approve their own apps' requests | One administrator is enough to approve, their own requests included; there is no quorum | Out of scope for #102 |
| A connection without a lifetime outlives its token | The token's 1 hour to 7 days bounds when it can be used to connect. A connection issued without a lifetime, the default and every connection made before #98, lasts until `logout`, revocation, or its member's removal or demotion. A lifetime cannot be extended | Not planned: an administrator sets a lifetime when issuing (#98) |
| A restore brings back members and roles as at the backup | Members removed or made viewers since the backup are back, with their old roles, until an administrator corrects the team. Their connections and tokens are revoked by the restore (T15), so they cannot sign through an app until a new token is issued, but they can sign in to the console | Not planned: `docs/operating.md` says to check **Team** after a restore |
| Backups leave the host only if the operator copies them | Bancwr writes archives to standard output and uploads nothing. Losing the host loses every archive kept on it | Not planned |
| An administrator can shorten retention, and so remove history | Down to 30 days or 10,000 rows, the change and each prune recorded (T16). Earlier exports and backups keep what was pruned. Without a policy the log grows without limit, in `./data` and in every archive | Not planned: `docs/operating.md` says to export first |
| The log is not tamper-evident | Whoever controls the host (X8) can edit or delete rows in SQLite, and the change shows nowhere. Audit events are not signed or hash-chained | Not planned |
| An export is outside Bancwr once downloaded | It names members, apps and when they signed. It holds no signing key and no event content | Not planned: `docs/operating.md` says so |
| A decrypt grant covers every message to the bunker's key | An app allowed `nip44_decrypt` or `nip04_decrypt` can read every encrypted message sent to the brand, from anyone. Each decrypt is recorded (T16), and revoking the connection stops it | Not planned in 0.2.0: restricting decryption to particular peers is out of scope for #97 |
| App metadata is self-reported | An app can name itself anything; Bancwr shows it as unverified | Not planned |
| The member's signer decides which key signs in | Some extensions keep using the key first connected to a site (README, "Signing in"; #70) | Not planned |
| `NIP46_RELAYS` is not checked for `wss://` | An operator who sets it can point the bunker at a remote `ws://` relay. NIP-46 content stays encrypted end to end, but anyone on the path can see who talks to the bunker and when | Not planned: the console's relay setting enforces it |
| TLS is the operator's reverse proxy | Bancwr refuses plain HTTP outside localhost but cannot check the proxy's configuration | Not planned |
| The host is trusted | Whoever controls the host's environment and files controls A1 (through A10), A3, A4 and A9, and so the bunker | Not planned |
| Images are not signed and have no SBOM or checksums | A pulled image cannot yet be verified against the release | #104 |
| No independent security review | This document is the maintainers' own analysis | diogel-io/workspace#175 |
